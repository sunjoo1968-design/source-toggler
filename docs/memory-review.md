# Camera MIX Controller 1.3.4 메모리 검토 및 개선

검토일: 2026-10-07 · 제작자: SunjooAn

## 결과

정적 검토와 모의 반복 테스트 범위에서는 반복 적용·전환·재로드에 따른 참조 누수를 발견하지 못했다. 실제 OBS 프로세스의 장시간 메모리 사용량이나 GPU 메모리가 일정하다는 의미는 아니다.

`tests/memory-stress.lua`를 OBS에 포함된 LuaJIT으로 실행했다. 기존 회귀 시나리오를 실행한 다음, 로드/언로드 100회, 전체 적용 1,000회, 카메라 선택 요청 3,000회를 추가 실행했다. 매 적용 후 private view 수가 설정된 카메라 수와 같고, 매 언로드 후 데이터·소스·sceneitem의 명시적 참조와 private view 수가 0으로 돌아오는지 확인했다. 타이머·프런트엔드 콜백·단축키 등록도 남지 않았다.

모의 API는 OBS의 실제 전환 대상 참조, 렌더링 텍스처, 드라이버 메모리를 완전히 재현하지 않는다. 테스트의 참조 카운터는 컨트롤러가 획득한 명시적 참조를 검사하며, OBS 장면 컬렉션이 보유한 모든 객체의 소멸을 검사하지 않는다. 테스트 기록 자체가 이전 엔진을 붙잡지 않도록 모의 이벤트 기록을 반복마다 비웠다.

## 확인한 정리 구조

- 엔진 재생성 전에 기존 전환 엔진을 해제한다.
- 전환 대상은 `obs_transition_clear`로 분리한 후 Fade 소스를 해제하고 private view를 해제한다.
- 런타임 출력 item과 원래 출력 item의 추가 참조를 해제한다.
- 조회한 소스, 설정 데이터, 배열, 열거 목록의 해제 경로가 있다.
- 언로드 시 모든 ME 엔진, 보류한 출력 소스, 설정 데이터, 타이머, 이벤트 콜백, 단축키를 정리한다.

## 개선 후보: 비활성 ME의 자원 유지

`script_update`에서 `me_count`를 줄이면 비활성화된 ME의 기존 엔진을 즉시 해제하지 않는다. 해당 엔진은 다시 전체 적용으로 재구성되거나 스크립트를 언로드할 때 정리되며, 사용 개수를 줄인 것만으로는 정리되지 않는다. ME 수는 최대 8개로 제한되고 각 bank에는 엔진 하나만 보관하므로 이 경로가 반복마다 새 엔진을 끝없이 쌓는 구조는 아니다. 다만 비활성 ME의 Fade와 private view가 원본 그룹 참조를 유지하므로 불필요한 자원 유지가 될 수 있다.

1.3.4에서 ME 사용 개수를 줄일 때 제외된 ME의 런타임 엔진을 즉시 해제하고, 다시 활성화하면 타이머에서 자동 복원하도록 수정했다. 마지막 선택과 사용자 배치·자막이 들어 있는 저장된 그룹은 유지한다. 위 자원 유지 설명은 1.3.3의 검토 결과이며 1.3.4에서는 해결됐다. 추가로 ME 축소/복원을 1,000회 반복하며 private view 즉시 해제, 출력 연결 복원, 선택·배치·자막 보존을 검증했다. 별도 libobs/D3D11 픽셀 테스트도 통과했다.

카메라 수를 줄일 때 숨겨진 기존 그룹을 남기는 동작은 추가 자막·장면·배치 보존을 위한 의도된 동작이다. 불필요한 그룹이 많으면 장면 자원은 유지되지만, 이를 자동 삭제하는 것은 사용자 데이터 보존 정책과 별도로 결정해야 한다.

## 추가 실환경 확인

현장 OBS를 종료하거나 재시작하지 않았다. 확정적인 실환경 누수 판정에는 별도 OBS 환경에서 동일 장면 컬렉션을 사용하고, 준비 실행 후 동일한 전환·적용 사이클을 반복하면서 프로세스 Private Bytes와 GPU 전용 메모리 추세를 측정해야 한다. 초기 캐시 증가와 반복마다 계속되는 증가를 구분해야 한다.
